# 输出与 Agent 评估标准

## 目的

本文用于定义本项目如何评估“小说转剧本”输出质量，以及如何评估负责生成剧本的 Agent 是否完成了竞赛任务。

评估标准来自 `docs/竞赛文档.md` 的硬约束和评审规则，并结合本项目目标：把 3 个章节以上的小说文本转换为可编辑、可继续打磨的 YAML 结构化剧本初稿。

## 赛题最低合格线

竞赛最终 Demo 生成结果必须先满足以下最低要求，否则视为未完成核心任务：

1. 最终演示输入必须来自 3 个章节以上的小说文本。
2. 输出必须是 YAML 格式，而不是 Markdown、纯文本或聊天式回答。
3. 输出必须是结构化剧本初稿，而不是小说摘要或读后感。
4. YAML 必须能被解析。
5. YAML 结构必须能对应项目定义的 YAML Schema。
6. 输出内容必须可编辑、可进一步打磨。
7. 生成过程和结果不得侵犯知识产权，不得抄袭第三方作品。

## 输出质量评估维度

### 1. 合规性

合规性是最高优先级。输出必须满足竞赛硬约束。

检查项：

- 最终 Demo 是否明确覆盖 3 个及以上章节。
- 是否输出合法 YAML。
- 是否符合项目 YAML Schema。
- 是否包含剧本所需的结构化字段。
- 是否保留可编辑字段，而不是只生成不可拆分的大段文本。

建议自动化校验：

- YAML 解析成功。
- Schema 校验通过。
- `source.chapters` 数量不少于 1；最终 Demo 和竞赛合规评分要求不少于 3。
- `characters` 不为空。
- `scenes` 不为空。
- 每个 scene 至少包含来源章节、时间、地点、出场人物和剧本内容。

### 2. 剧本化程度

输出应体现从小说叙事到剧本表达的改编，而不是简单摘要。

检查项：

- 是否拆分为合理场景。
- 是否包含时间、地点、人物、动作、对白等剧本元素。
- 是否把心理描写转换为可表演动作、对白或场景调度。
- 是否减少大段小说式旁白。
- 是否保留关键冲突和戏剧推进。

示例判断：

- 较差：`林舟很害怕。`
- 较好：`林舟停在门口，手指悬在门铃上，迟迟没有按下。`

### 3. 原文忠实度

剧本初稿应忠实于小说核心内容，允许必要的剧本化改写，但不能随意改变主线。

检查项：

- 主线剧情是否保留。
- 关键事件是否完整。
- 人物关系是否一致。
- 场景顺序是否合理。
- 新增内容是否服务于剧本表达。
- 是否标注每个场景对应的来源章节或来源情节。

建议在 YAML 中保留 `source_ref`、`chapter_source` 或类似字段，用于说明剧本场景来自哪些章节。

### 4. 结构完整度

YAML 输出应能支持后续编辑、校验、导出和二次加工。

建议包含：

- `metadata`：标题、生成时间、版本等。
- `source`：输入章节信息、章节摘要。
- `characters`：人物表、人物 ID、角色定位、人物描述。
- `locations`：主要地点。
- `plot_summary`：整体故事梗概。
- `scenes`：剧本场景列表。
- `beats`：每个场景中的动作、对白、旁白或转场。
- `adaptation_notes`：改编说明或待人工确认事项。

结构越稳定，越能体现工程质量和 Schema 设计合理性。

### 5. 可编辑性

输出目标是“剧本初稿”，不是最终定稿。结构必须方便小说作者继续修改。

检查项：

- 人物、场景、对白有稳定 ID。
- 对白明确 speaker。
- 动作、对白、旁白、转场有明确 type。
- 场景可以单独增删改。
- 人物引用一致，避免同一人物多种命名。
- 字段名清晰，非技术用户也能理解。

### 6. 多章节一致性

3 个章节以上输入会引入跨章节一致性问题，这是评估 Agent 能力的重要维度。

检查项：

- 同一人物在不同章节中 ID 一致。
- 人物设定、关系、称呼前后一致。
- 地点名称前后一致。
- 前文事件能被后文正确继承。
- 剧本场景顺序与故事发展一致。
- 不遗漏关键章节。

建议实现人物设定表、剧情记忆表或章节摘要中间结果，以减少长文本生成时的信息漂移。

### 7. 可验证性

优秀输出应能被工具自动检查，而不是只依赖人工主观判断。

建议校验项：

- YAML parse 校验。
- YAML Schema 校验。
- 章节覆盖率。
- 场景字段完整率。
- 人物引用合法性。
- 对白 speaker 是否存在于人物表。
- scene 的 `chapter_source` 是否能对应输入章节。
- 输出中是否存在空字段或明显占位符。

## Agent 评估标准

这里的 Agent 指负责把小说输入转换为 YAML 剧本输出的生成流程，可以是单个模型调用，也可以是多阶段 Agent pipeline。

### 1. 任务完成度

- 能否处理 3 个章节以上小说文本；产品试用场景允许 1-2 章输入生成结构化初稿。
- 能否产出合法 YAML。
- 能否产出符合 Schema 的结构化剧本。
- 能否提供可编辑初稿，而不是最终不可拆文本。

### 2. 流程可靠性

- 是否采用分阶段处理，而不是一次性把长文本全部交给模型。
- 是否有章节解析、摘要、人物抽取、场景拆分、剧本生成、YAML 校验等步骤。
- 是否能在 YAML 不合法或 Schema 不通过时自动修复。
- 是否能给出错误信息，帮助用户修改输入。

### 3. 改编质量

- 是否忠实保留原文主线。
- 是否生成有剧本感的动作和对白。
- 是否保留故事冲突和人物动机。
- 是否避免凭空创造与原文冲突的设定。
- 是否能把小说心理描写转换为可表演表达。

### 4. 一致性控制

- 是否维护人物表。
- 是否维护地点表。
- 是否维护跨章节剧情摘要。
- 是否在剧本场景中引用统一人物 ID。
- 是否避免人物、地点、时间线混乱。

### 5. 可解释性

- 是否能展示中间产物，例如章节摘要、人物列表、场景拆分。
- 是否能说明每个场景来源于哪些章节。
- 是否能输出 `adaptation_notes`，标记模型不确定或需要人工确认的地方。

### 6. 工程可评估性

- 是否有测试样例。
- 是否有示例输入和示例输出。
- 是否有自动校验脚本。
- 是否在 README 中说明依赖、原创功能和运行方式。
- 是否能在 Demo 中稳定复现。

## 建议评分表

总分 100，用于内部自测和 Demo 前验收。

| 维度         | 分值 | 通过标准                                           |
| ------------ | ---: | -------------------------------------------------- |
| 赛题合规性   |   20 | 支持 3+ 章节输入，输出 YAML，符合 Schema           |
| 剧本化程度   |   20 | 场景、动作、对白、冲突清晰，不只是摘要             |
| 原文忠实度   |   15 | 主线、人物关系、关键事件基本准确                   |
| 结构完整度   |   15 | metadata/source/characters/scenes/beats 等结构完整 |
| 可编辑性     |   10 | 字段清晰、ID 稳定、场景和对白可独立修改            |
| 多章节一致性 |   10 | 人物、地点、时间线跨章节一致                       |
| 可验证性     |   10 | YAML parse、Schema 校验、引用校验可执行            |

低于 70 分的输出不适合作为 Demo 结果。Demo 推荐使用 85 分以上的样例。

## Demo 验收清单

Demo 前至少完成以下检查：

1. 使用 3 个以上章节的小说样例。
2. 成功生成 YAML 结构化剧本。
3. YAML 能被解析。
4. YAML Schema 校验通过。
5. 至少展示人物表、场景列表、对白或动作 beats。
6. 至少展示一个场景与原文章节的对应关系。
7. 展示用户可编辑或可导出 YAML。
8. README 中列出依赖、原创功能和 Demo 视频链接。
9. 仓库 commit 与 PR 记录持续、清晰、符合竞赛要求。

## 加分方向

优先级从高到低：

1. YAML Schema 校验和自动修复。
2. 多阶段转换流程：章节解析、摘要、人物抽取、场景拆分、剧本生成、校验。
3. 原文到剧本的来源映射。
4. 人物一致性管理。
5. 可编辑剧本工作台。
6. 输出质量评分面板。
7. 多种改编风格，例如影视剧本、短剧剧本、舞台剧本。
8. 示例输入、示例输出和一键复现 Demo。

# 成熟剧本格式调研

## 调研目的

本项目的最终交付物是 YAML 格式的结构化剧本初稿。赛题没有要求输出传统剧本文档排版，但要求输出可编辑、可继续打磨的剧本。因此，本调研用于回答两个问题：

- 成熟剧本通常由哪些稳定元素组成。
- 当前 `schemas/script.schema.json` 应该如何吸收这些元素，同时保留小说改编工具需要的来源追踪和质量评估能力。

## 参考资料

本次调研优先参考剧本软件、剧本写作机构和开放剧本标记规范：

- BBC Writersroom screenplay format PDF：`https://downloads.bbc.co.uk/writersroom/scripts/screenplay.pdf`
- Final Draft screenplay elements：`https://kb.finaldraft.com/hc/en-us/articles/27646947570196-What-are-script-elements`
- Final Draft screenplay formatting guide：`https://www.finaldraft.com/learn/screenplay-formatting-elements/`
- Fountain screenplay syntax：`https://fountain.io/syntax/`

这些资料的共同点是：剧本不是小说段落的简单重写，而是由场景标题、动作、人物提示、对白、括号提示和转场等元素组成的可拍摄文本。

## 成熟剧本的核心元素

### 1. 场景标题

成熟剧本通常用场景标题标明一个场景的空间和时间信息。常见结构是：

```text
INT. LOCATION - DAY
EXT. LOCATION - NIGHT
```

其中：

- `INT.` 表示内景。
- `EXT.` 表示外景。
- `LOCATION` 表示具体地点。
- `DAY`、`NIGHT` 或更细的时间词表示时间段。

对本项目的启发：

- 当前 Schema 已有 `scene.location_id` 和 `scene.time_of_day`。
- 后续可以补充 `scene.setting_type`，取值如 `interior`、`exterior`、`interior_exterior`、`unspecified`。
- 后续也可以增加只读或导出用字段 `scene_heading`，由地点、内外景和时间自动拼接。

### 2. 动作

动作描述用于说明观众能看见或听见的内容，应避免小说式心理描写和冗长背景解释。BBC 和 Final Draft 的格式说明都强调动作应服务画面，而不是把小说叙述原样搬进剧本。

对本项目的启发：

- 当前 `beats.type = action` 是必要字段类型，应继续保留。
- 质量评估应关注动作是否可表演、可视化，而不是只检查字段存在。
- 模型提示词应要求 action beat 少写心理活动，多写行为、环境变化和可见冲突。

### 3. 人物提示与对白

成熟剧本中，对白前通常有明确的人物提示，人物名称需要保持一致。对白本身跟随人物提示出现，不能脱离说话人单独存在。

对本项目的启发：

- 当前 `dialogue` beat 要求 `speaker_id`，方向是正确的。
- `speaker_id` 使用稳定人物 ID，比直接使用角色名更适合机器校验和 UI 编辑。
- 校验逻辑应继续保证 `speaker_id` 能在全局人物表中找到，最好也能出现在当前场景的 `characters` 中。

### 4. 括号提示

括号提示通常用于补充对白的递送方式、短动作或情绪，但成熟剧本资料普遍建议少用，避免过度指导演员。

对本项目的启发：

- 当前 Schema 有 `beat.emotion`，但没有单独的 `parenthetical`。
- 短期可以继续用 `emotion` 承载轻量表演提示。
- 如果后续需要更贴近行业剧本，可把 dialogue beat 扩展为：

```yaml
- type: dialogue
  speaker_id: character_001
  parenthetical: 低声
  content: 我们不能再等了。
```

### 5. 转场

转场用于标记场景之间的切换方式。现代剧本一般不需要每个场景都显式写 `CUT TO`，只有风格化或必要的转场才需要写出。

对本项目的启发：

- 当前 `beats.type = transition` 可以保留，但模型不应滥用。
- 质量评估可以把过多的 transition 视为可读性风险。
- 生成提示词应把转场定义为可选元素，而不是每个场景结尾强制生成。

### 6. 镜头与拍摄指令

Final Draft 把 shot 也列为脚本元素，但它更偏向拍摄层面。竞赛要求的是剧本初稿，不是分镜或制片方案。

对本项目的启发：

- 第一版 Schema 不应加入大量镜头、机位、景别字段。
- 如果后续要做增强功能，可以新增可选 `shot` beat，但不应作为核心必填项。

### 7. 幕、页和排版

传统剧本会关注页边距、分页、页码、幕结构和导出排版。Fountain 这类开放标记规范也支持标题页、分页、section、synopsis 等信息。

对本项目的启发：

- YAML 交付物不需要直接复刻页边距和缩进。
- `metadata` 已承担标题、版本、语言、目标格式等元信息。
- 长篇小说改编时，可以考虑增加可选 `acts` 或 `sequences`，但当前 Demo 优先保证章节到场景的闭环。

## 当前 Schema 与成熟剧本元素的映射

| 成熟剧本元素    | 当前 YAML 字段                                 | 当前状态 | 说明                                       |
| --------------- | ---------------------------------------------- | -------- | ------------------------------------------ |
| 标题页/项目信息 | `metadata`                                     | 已覆盖   | 记录标题、版本、语言、目标格式             |
| 场景标题        | `scenes[].title`、`location_id`、`time_of_day` | 部分覆盖 | 缺少内外景字段和标准化 scene heading       |
| 动作            | `beats[].type = action`                        | 已覆盖   | 可继续加强“可视化动作”评分                 |
| 人物提示        | `characters`、`speaker_id`                     | 已覆盖   | 使用稳定 ID 适合结构化校验                 |
| 对白            | `beats[].type = dialogue`                      | 已覆盖   | dialogue 必须有 `speaker_id`               |
| 括号提示        | `beats[].emotion`                              | 部分覆盖 | 可考虑新增 `parenthetical`                 |
| 转场            | `beats[].type = transition`                    | 已覆盖   | 应少量使用                                 |
| 镜头            | 无                                             | 暂不覆盖 | 剧本初稿阶段不强制需要                     |
| 来源追踪        | `source`、`chapter_source`、`source_ref`       | 项目增强 | 成熟剧本通常没有，但小说改编和竞赛评估需要 |

## 当前 Schema 的合理性判断

当前 Schema 不是对成熟剧本格式的逐字复制，而是把成熟剧本的核心元素抽象成可编辑、可校验的数据结构。这个方向是合理的，原因如下：

- 赛题明确要求 YAML，而不是 PDF、Final Draft 文档或 Fountain 文本。
- 小说作者需要继续编辑，结构化字段比一整段剧本文本更适合 UI 工作台。
- 竞赛评估需要证明输入章节被覆盖，传统剧本格式没有 `chapter_source`，本项目必须额外保留来源映射。
- Schema 校验、质量评分和 Demo 展示都依赖稳定字段和 ID 引用。

但当前 Schema 仍有改进空间：

- 场景标题还不够行业化，缺少内外景结构。
- dialogue beat 缺少标准括号提示字段。
- 生成提示词需要更明确要求 action beat 避免小说式心理描写。
- 对 3 个以上章节的输入，场景输出必须覆盖所有章节，而不是只处理前 3 章。

## 建议调整

### 必做

1. 保持产品支持 1 章以上生成，并在竞赛 Demo 和评分中明确检查 `source.chapter_count >= 3`。
2. 生成逻辑必须覆盖所有输入章节。可以多个章节合并成一个场景，但每个 `chapter_id` 至少要出现在一个 `scene.chapter_source` 中。
3. 修改模型提示词，明确动作要写“可看见、可听见、可表演”的内容，减少小说式内心独白。

### 推荐

1. 为 scene 增加可选字段：

```yaml
setting_type: interior
scene_heading: INT. 档案馆走廊 - 深夜
```

2. 为 dialogue beat 增加可选字段：

```yaml
parenthetical: 压低声音
```

3. 在质量评分中增加两个软性指标：

- 动作可视化程度。
- 旁白和转场是否过量。

### 暂不建议

1. 暂不加入强制镜头、机位、景别字段。
2. 暂不要求完全模拟 Final Draft 页边距和分页。
3. 暂不把 YAML 改成 Fountain，因为赛题交付核心是 YAML Schema 和结构化剧本。

## 结论

当前 YAML Schema 的主体方向是正确的：它以成熟剧本的场景、动作、对白、转场为基础，又增加了小说改编特有的章节来源追踪和质量评估字段。

下一步不需要推翻 Schema，而应该做小步增强：

- 修复 3 个以上章节输出覆盖问题。
- 增加内外景和可选标准场景标题。
- 增加可选括号提示。
- 更新生成提示词和质量评分，让输出更像剧本，而不是小说摘要。

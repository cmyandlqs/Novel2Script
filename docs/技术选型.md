# 技术选型

## 当前状态

当前仓库尚未落地应用代码，只有竞赛文档、评估标准、开发计划和 agent 协作说明。因此本文定义的是本项目后续实现时采用的目标技术形态与技术栈。

目标不是堆叠复杂技术，而是服务竞赛要求：稳定完成 3 个章节以上小说文本输入、AI 辅助改编、YAML 结构化剧本输出、Schema 校验、可编辑导出和可复现 Demo。

## 推荐项目形态

本项目采用前后端一体的 Web 工具形态：

```text
小说作者在浏览器中使用
-> 粘贴或上传 3+ 章节小说
-> 解析章节
-> 调用 AI 改编流程
-> 输出 YAML 结构化剧本
-> 校验 Schema
-> 编辑剧本
-> 导出 YAML
```

不采用 CLI 作为主形态，因为 CLI 难以展示面向小说作者的交互体验，也不利于 Demo 表达“产品完整度与创新性”。

不采用前后端完全分离作为第一版，因为会增加启动、部署、联调成本。竞赛优先级是完整闭环、可运行、可复现，而不是复杂工程拆分。

不在第一版引入数据库和用户系统，因为赛题没有要求登录、历史记录或多人协作。存储能力可以后续增强，但不应阻塞核心闭环。

## 目标技术栈

```text
框架：Next.js App Router
语言：TypeScript
UI：React + Tailwind CSS
服务端接口：Next.js Route Handlers
YAML 处理：yaml
Schema 校验：AJV + JSON Schema
测试：Vitest
AI 层：Provider Adapter，包括 MockProvider 和真实 LLM Provider
部署：Vercel 或普通 Node.js 环境
```

## 选型理由

### Next.js App Router

Next.js 适合做本项目的前后端一体 Web 工具。它可以在一个仓库中同时提供页面、服务端接口、环境变量管理和部署入口。

在本项目中，Next.js 负责：

- 主工作台页面。
- 章节解析、剧本生成、YAML 校验等 API route。
- 本地开发与部署。
- Demo 环境的一体化启动。

这样可以减少 `frontend/` 与 `backend/` 两套工程之间的联调成本。

### TypeScript

本项目天然依赖大量结构化数据：

- `Chapter`
- `Character`
- `Location`
- `Scene`
- `Beat`
- `ScriptYaml`
- `ValidationResult`
- `QualityScore`

TypeScript 可以把这些结构变成稳定类型，减少生成流程、校验流程和 UI 编辑之间的数据错配。

### React

React 用于构建可编辑剧本工作台。核心界面不是展示页，而是工具界面：

- 小说输入区。
- 章节解析结果区。
- 人物表。
- 场景列表。
- beats 编辑区。
- YAML 预览区。
- 校验与评分面板。

### Tailwind CSS

Tailwind CSS 用于快速构建工具型 UI。界面应保持清晰、紧凑、可扫描，避免营销页风格。

设计重点：

- 第一屏就是可用工具。
- 不做大面积 hero、装饰卡片或无关视觉效果。
- 控件服务编辑和校验流程。
- 移动端和桌面端都不应出现文字溢出或重叠。

### yaml

赛题硬约束要求输出 YAML。项目不能只把模型输出字符串展示出来，必须能解析、校验、编辑和重新序列化。

`yaml` 包用于：

- 解析模型输出 YAML。
- 将编辑后的结构化对象序列化回 YAML。
- 检测 YAML 语法错误。
- 支持示例 YAML 和导出 YAML。

### AJV + JSON Schema

赛题要求提交 YAML Schema 定义文档，并说明设计原因。工程实现上，YAML 会先解析为对象，再用 JSON Schema 校验对象结构。

AJV 用于：

- 校验生成结果是否符合 `schemas/script.schema.json`。
- 输出字段缺失、类型错误、枚举错误等结构问题。
- 支撑质量评分面板中的合规性检查。

### Vitest

Vitest 用于覆盖核心纯逻辑模块：

- 章节解析。
- 3+ 章节输入校验。
- YAML parse。
- Schema validation。
- 人物引用一致性。
- 质量评分。

这些测试能直接支撑竞赛“开发过程与质量”评分。

### AI Provider Adapter

AI 层不直接写死某一个模型，而是通过 provider adapter 隔离：

```text
ScriptGenerationProvider
├── MockProvider
├── OpenAIProvider
└── CompatibleProvider
```

这样做的原因：

- 无 API Key 时也能通过 MockProvider 完成 Demo。
- 真实模型调用失败时不影响基础演示。
- 后续可以替换模型供应商。
- 单元测试不依赖外部网络和模型质量。
- 生成流程、校验流程和 UI 流程可以先于真实 LLM 接入完成。

## 第一版不做的内容

为保证竞赛核心闭环稳定，第一版暂不实现：

- 用户登录。
- 数据库持久化。
- 多用户协作。
- 复杂富文本编辑器。
- 复杂项目管理或历史版本系统。
- 完全前后端分离架构。

这些能力可以作为后续增强，但不应优先于输入、生成、YAML、Schema 校验、编辑和导出。

## 技术风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| LLM 输出 YAML 不稳定 | Demo 失败或校验不通过 | 使用 Schema 约束、校验、自动修复和 MockProvider |
| 长文本一次生成质量差 | 人物和剧情不一致 | 使用章节摘要、人物抽取、场景拆分等多阶段 pipeline |
| API Key 或模型服务不可用 | Demo 受阻 | MockProvider 作为兜底 |
| UI 过度复杂 | 开发延期 | 第一版只做结构化编辑，不做富文本 |
| 第三方依赖未说明 | 触发竞赛无效风险 | README 中列明依赖和原创功能 |

## 结论

本项目采用 Next.js + TypeScript 的前后端一体 Web 工具形态。核心技术选择围绕竞赛硬约束展开：用 YAML 和 AJV 保障结构化输出和 Schema 校验，用多阶段 AI Provider Pipeline 提升生成稳定性，用 React 工作台承载小说作者的编辑与导出体验。

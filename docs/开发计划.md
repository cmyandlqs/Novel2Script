# 开发计划

## 目标

本项目要完成一个面向小说作者的 AI 小说转剧本工具。核心闭环是：输入 3 个章节以上的小说文本，经过 AI 辅助分析和改编，输出可编辑、可继续打磨的 YAML 结构化剧本初稿，并提供 YAML Schema 定义和设计说明。

开发计划必须同时服务三个目标：

1. 满足 `docs/竞赛文档.md` 中的硬约束。
2. 满足 `docs/输出与Agent评估标准.md` 中的输出质量和 Agent 评估要求。
3. 形成持续、清晰、可审查的 PR 与 commit 记录。

## 总体产品闭环

```text
3+ 章节小说输入
-> 章节解析与输入校验
-> 章节摘要
-> 人物/地点/事件抽取
-> 场景拆分
-> YAML 剧本生成
-> YAML parse 校验
-> YAML Schema 校验
-> 质量评分与问题提示
-> 可编辑剧本工作台
-> YAML 导出
```

## 技术形态与选型

项目采用前后端一体的 Web 工具形态。目标技术栈为 Next.js App Router、TypeScript、React、Tailwind CSS、`yaml`、AJV、Vitest，以及可替换的 AI Provider Adapter。

详细选型依据见 `docs/技术选型.md`。

第一版不引入数据库、用户系统、复杂富文本编辑器或完全前后端分离架构。优先保证输入、生成、YAML 输出、Schema 校验、编辑和导出闭环稳定可演示。

## 阶段 0：竞赛与工程约束固化

### 做什么

- 保持仓库在开发阶段为 private。
- 继续维护 `CLAUDE.md`、`AGENTS.md` 和竞赛相关 docs。
- 以小粒度 commit 和 PR 推进开发。
- 确保每次主分支合并后都可运行。

### 怎么做

- 每个功能拆成一个独立分支和 PR。
- PR 标题说明本次新增或修改了什么。
- PR 描述必须包含功能描述、实现思路、测试方式。
- commit 使用 `docs:`、`feat:`、`fix:`、`test:`、`refactor:`、`chore:` 等前缀。
- 不提交 `.env`、密钥、构建产物或本地无关配置。

### 验收标准

- 仓库可见性为 private。
- 本地 `main` 与 `origin/main` 同步。
- 根目录 agent 文档内容一致。
- 文档中明确竞赛硬约束、仓库信息和目录说明。

### 注意事项

- 不要在竞赛允许公开前把仓库改成 public。
- 不要最后一天一次性导入全部代码。
- 不要为了赶进度跳过 PR 描述和测试记录。

## 阶段 1：YAML Schema 与输出契约

### 做什么

- 定义 YAML 剧本输出结构。
- 新增 JSON Schema 文件，例如 `schemas/script.schema.json`。
- 新增 Schema 设计说明，例如 `docs/YAML_Schema设计说明.md`。
- 新增合法输出示例，例如 `examples/output-script.yaml`。

### 怎么做

- Schema 覆盖以下核心模块：
  - `metadata`：标题、版本、生成时间等。
  - `source`：输入章节、章节摘要、章节数量。
  - `characters`：人物 ID、姓名、角色定位、描述。
  - `locations`：地点 ID、名称、描述。
  - `plot_summary`：整体故事梗概。
  - `scenes`：场景 ID、来源章节、时间、地点、人物、场景目标。
  - `beats`：动作、对白、旁白、转场等剧本内容。
  - `adaptation_notes`：改编说明和待人工确认事项。
- 人物、地点、场景都使用稳定 ID。
- 场景中的人物引用必须对应 `characters` 中已定义人物。
- `beats.type` 使用有限枚举，例如 `action`、`dialogue`、`narration`、`transition`。

### 验收标准

- 示例 YAML 能被解析。
- 示例 YAML 能通过 Schema 校验。
- Schema 文档解释每个核心字段的设计原因。
- Schema 体现“可编辑、可进一步打磨”的剧本初稿定位。

### 注意事项

- 不要让 Schema 过度复杂，第一版优先服务核心闭环。
- 不要把输出设计成纯文本字段，否则无法体现结构化。
- Schema 是后续生成、校验、UI 编辑的共同契约，应优先稳定。

## 阶段 2：工程骨架与基础运行

### 做什么

- 初始化可运行 Web 应用。
- 新增基础 README、`.gitignore`、运行脚本。
- 实现第一版工具页面。

### 怎么做

- 优先采用前后端一体方案，降低部署和 Demo 成本。
- 页面第一屏就是实际工具，不做营销页。
- 初始页面包含：
  - 小说输入区。
  - 章节解析结果区。
  - 生成按钮。
  - YAML 输出区。
  - 校验状态区。
- 先使用 mock 输出打通页面，不依赖真实 LLM。

### 验收标准

- 安装依赖成功。
- 开发服务器能启动。
- 页面能打开。
- 输入样例后能显示 mock YAML 输出。
- README 包含项目介绍和基础运行方式。

### 注意事项

- 主分支必须随时可运行。
- 不要在这个阶段引入复杂状态管理或大型框架组合。
- 依赖必须在 README 中说明。

## 阶段 3：章节解析与输入校验

### 做什么

- 实现小说章节解析。
- 校验输入必须包含 3 个以上章节。
- 展示章节标题、字数和解析结果。

### 怎么做

- 支持常见章节格式：
  - `第1章`
  - `第一章`
  - `Chapter 1`
  - Markdown 标题
- 如果没有明确章节标题，支持按分隔符或手动章节块处理。
- 提供输入错误提示，例如“当前仅识别到 2 个章节，至少需要 3 个章节”。
- 为章节解析添加单元测试。

### 验收标准

- 3 章及以上输入通过校验。
- 少于 3 章输入被拒绝。
- 页面展示章节数量和每章基本信息。
- 章节解析测试通过。

### 注意事项

- 不要只靠前端提示，核心解析逻辑应可测试。
- 不要把章节切分写死到单一样例。
- 后续 Agent pipeline 必须使用解析后的章节结构。

## 阶段 4：多阶段 Agent Pipeline

### 做什么

- 实现小说转剧本的多阶段生成流程。
- 支持 mock provider 和真实 LLM provider。
- 保留中间产物用于展示和调试。

### 怎么做

- 定义统一转换接口，例如：
  - 输入：章节数组、改编风格、输出选项。
  - 输出：章节摘要、人物表、地点表、场景拆分、YAML 剧本。
- Pipeline 推荐步骤：
  1. 章节摘要。
  2. 人物抽取。
  3. 地点和关键事件抽取。
  4. 场景拆分。
  5. YAML 剧本生成。
  6. YAML 校验。
  7. 必要时自动修复。
- mock provider 用固定样例输出，保证无 API Key 也能演示。
- 真实 provider 通过环境变量配置 API Key，不把密钥提交到仓库。

### 验收标准

- 无 API Key 时 mock pipeline 能跑完整流程。
- 有 API Key 时能调用真实模型生成结果。
- 页面能展示至少一种中间产物，例如人物表或场景拆分。
- 生成失败时有明确错误提示。

### 注意事项

- 不要一次性把全部长文本直接交给模型生成最终 YAML。
- prompt 必须围绕 Schema 输出，减少自由发挥。
- 真实 LLM 结果必须经过校验，不允许直接作为最终结果展示。

## 阶段 5：YAML 校验与质量评分

### 做什么

- 实现 YAML parse 校验。
- 实现 Schema 校验。
- 实现引用一致性和章节覆盖校验。
- 实现输出质量评分面板。

### 怎么做

- 使用 YAML 解析库检查输出是否合法。
- 使用 JSON Schema 校验库检查结构是否符合 `schemas/script.schema.json`。
- 自定义业务校验：
  - `source.chapters` 数量不少于 3。
  - `characters` 不为空。
  - `scenes` 不为空。
  - 每个 scene 有来源章节、时间、地点、出场人物和 beats。
  - dialogue 的 speaker 必须存在于人物表。
  - scene 引用的角色 ID 必须存在。
- 将 `docs/输出与Agent评估标准.md` 的评分维度映射到页面评分。

### 验收标准

- 非法 YAML 能显示解析错误。
- 不符合 Schema 的 YAML 能显示错误路径。
- 合法示例 YAML 校验通过。
- 页面显示合规性、结构完整度、可编辑性等评分或检查结果。

### 注意事项

- 校验结果要面向用户可理解，不只显示底层错误对象。
- 自动修复可以作为增强功能，但不能替代校验。
- 评分面板要服务 Demo，不要做成复杂评测系统。

## 阶段 6：可编辑剧本工作台

### 做什么

- 实现剧本编辑界面。
- 支持查看和修改人物、场景、beats。
- 支持复制和导出 YAML。

### 怎么做

- 页面布局建议：
  - 左侧：章节输入与解析结果。
  - 中间：人物表、场景列表、剧本 beats 编辑。
  - 右侧：YAML 预览和校验结果。
- 编辑结构化对象后重新序列化为 YAML。
- 修改后可重新运行校验。
- 支持下载 `.yaml` 文件。

### 验收标准

- 用户能修改人物名称或描述。
- 用户能修改场景地点、时间、摘要。
- 用户能修改动作或对白内容。
- 修改后 YAML 同步更新。
- 修改后可以重新校验并导出。

### 注意事项

- 第一版不要做复杂富文本编辑器。
- UI 要以工具效率为主，不做营销式页面。
- 字段名称要清晰，符合小说作者的理解习惯。

## 阶段 7：示例数据与可复现 Demo

### 做什么

- 准备原创 3+ 章节小说样例。
- 准备对应示例 YAML 输出。
- 准备 Demo 操作脚本。
- 确保无外部不稳定依赖时也能复现。

### 怎么做

- 将样例放入 `examples/`。
- 使用原创短篇，避免版权风险。
- Demo 流程固定为：
  1. 加载或粘贴 3+ 章节小说。
  2. 解析章节。
  3. 生成 YAML 剧本。
  4. 展示人物、场景和来源映射。
  5. 展示 Schema 校验通过。
  6. 编辑一处对白或场景。
  7. 导出 YAML。
- mock 模式作为演示兜底。

### 验收标准

- 样例输入不少于 3 个章节。
- 示例输出符合 Schema。
- Demo 流程能连续跑通。
- 按 `docs/输出与Agent评估标准.md` 内部评分建议达到 85 分以上。

### 注意事项

- 样例文本必须原创或确认可合法使用。
- 不要让 Demo 完全依赖实时模型质量。
- Demo 要展示“小说到剧本”的转换，而不是只展示 YAML 文本。
